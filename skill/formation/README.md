# Skill Source Map

| Directory | Responsibility |
| --- | --- |
| `core/` | Typed schemas, the execution engine (compile/frontier/dispatch/run state), the single-writer reducer, the autonomy evaluator, the scheduled-session runner, the founder provisioning CLI (`core/provisioning/`), and runtime adapters |
| `catalog/` | The definition graph as data — domains, lanes, workflows, gates, knowledge manifests, and presentation groups — and the routing renderer, whose output lands in `catalog/generated/` (`catalog.json`, `routing.md`, `spine.md`) |
| `knowledge/` | Bounded domain knowledge loaded by catalog context contracts |
| `content/` | Founder-facing conversation content (onboarding) rendered by the session |
| `workspace/`, `workspace-template/` | Reusable business artifacts copied into app repositories, and the v2 workspace/entrypoint templates |
| `validation/` | Business gates, repository checks, fixtures, LaunchBench, and the agent/behavioral eval suite (`validation/repository/evals/`) |
| `verification/` | The core's own proof — fixtures, the capability-boundary suite, parity, scenarios, rehearsal drills, and the audit runner |
| `tooling/` | Renderers, probes, migrations, and command-line utilities |
| `studio/` | Skill-owned visual studio source, seed state, and generated output |
| `starters/` | Runnable product-archetype foundations |
| `agents/` | Agent-runtime interface manifests (for example the OpenAI surface descriptor) |
| `bin/` | The packaged `formation` command — one installable dispatcher over the session CLIs (`setup`, `doctor`, `new`, `bootstrap`, `plan`, `run`, `approve`, `verify`, `onboard`, `schedule`, `workspaces`, `list`, `update`) — and `formation-mcp`, the same surface as a Model Context Protocol stdio server (`core/mcp/server.ts`) that resolves workspaces only through the `formation workspaces` registry; both add addresses, never a second implementation |

`SKILL.md` is the runtime entrypoint. `formation --help` is the command-line one. [`catalog/generated/spine.md`](./catalog/generated/spine.md) is the phase-oriented narrative, generated by `catalog/render-routing.ts`. Stable catalog IDs are identities; filesystem paths are bindings.

## The consumer journey

Every command below is shipped and fixture-proven; nothing here is aspirational. The engine
orchestrates YOUR agent CLIs (claude, codex, or cursor-agent) — your subscriptions, your spend.
`npm pack` of this package is standalone (`files` manifest, smoke-tested in
`check:package-parity`); distribution today is git-tag pinning — clone the repository at a tag
and `npm install` in this directory. Publishing to npm is a founder decision deliberately
deferred.

```bash
formation setup                                   # once per machine: home, registry, health checks
formation doctor                                  # read-only health report, any time
formation new corner-bakery --dir ~/biz/corner-bakery
formation bootstrap --workspace ~/biz/corner-bakery --apply --answers answers.json
formation workspaces register corner-bakery ~/biz/corner-bakery
formation plan --workspace corner-bakery-or-path  # what would run and why
formation run --workspace ~/biz/corner-bakery --brief brief.json --session s-001
formation approve --workspace ~/biz/corner-bakery --list
formation schedule --workspace ~/biz/corner-bakery --runtime claude --schedule "0 9 * * *" --apply
formation list                                    # every business with live run status
formation update                                  # engine update (dry-run); businesses re-pin via bootstrap --apply
```

The MCP address is the same surface over stdio: `claude mcp add formation -- node <this
directory>/bin/formation-mcp.mjs` (any MCP-capable runtime; `formation setup` prints the exact
path). The server resolves workspaces only through the registry, approval decisions and schedule
installs require an explicit `asFounder` assertion, and `FORMATION_MCP_READONLY=1` narrows the
surface to `formation_plan` and `formation_status`.

A workspace pins its own executable catalog. Updating the engine never changes a running
business; `formation bootstrap --workspace <dir> --apply` is the explicit, per-business re-pin,
and the drift is named in every dry-run until then.

## Knowledge Package Commands

- `npm run knowledge:add -- --id reference.<domain>.<name> --title "Title" --domain domain.<domain>` creates a draft document and manifest.
- `npm run knowledge:refresh -- --id reference.<domain>.<name>` creates a temporary review bundle. It does not change tracked files.
- `npm run knowledge:promote -- --id reference.<domain>.<name> --reviewer "Name"` promotes a reviewed draft.
- `npm run knowledge:check` validates lifecycle, provenance, freshness, paths, and graph bindings.

No command promotes new material automatically.
